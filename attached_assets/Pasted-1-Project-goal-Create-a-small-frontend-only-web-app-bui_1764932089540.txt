1. Project goal

Create a small, frontend-only web app built with React that allows users to compose fake conversations between two people and see them rendered as SMS-style chat screenshots.

No user accounts.

No backend or database.

Everything happens in the browser.

The app is split into:

Left side: a panel where the user defines the conversation (list of messages, who sends what).

Right side: a live visual preview that looks like a smartphone screen displaying the conversation.

2. Functional scope
2.1. Core features

Conversation definition

The user can create a list of messages.

For each message, the user can:

Choose the sender (Person A or Person B).

Enter the message text.

Live conversation preview

The conversation is displayed in a smartphone-like view.

Messages are shown as chat bubbles, visually differentiating the two senders.

Any change on the left (adding, editing, deleting, reordering messages, changing names) is reflected on the right in real time.

Two participants

There are exactly two participants in the conversation.

The user can optionally define a display name for each participant (e.g. “You” and “Friend”).

These names are used in the preview (e.g. as the conversation title/contact name).

3. Application behavior
3.1. Message management

The user should be able to:

Add a message

Select who sends the message (Person A or Person B).

Enter the text of the message.

Confirm to add it to the conversation.

Edit a message

Select an existing message.

Modify the text and/or sender.

Save the changes.

Delete a message

Remove a specific message from the conversation.

Reorder messages

Change the order of messages (to correct mistakes or adjust the flow of the conversation).

A simple mechanism is sufficient (e.g. move up / move down), but the exact interaction is up to you.

Validation expectations:

A message should not be added if its text is empty (at least whitespace should be ignored).

If validation fails, the user should understand why (e.g. a brief error or visual indication).

3.2. Participant names

The user can define a name/label for:

Person A.

Person B.

If no names are provided, use default labels (for example, “You” and “Friend” or similar).

These names are used in the preview, for example:

In the conversation header as the “contact” name.

They do not need to appear next to each bubble unless you decide it’s useful.

4. Layout and responsiveness
4.1. General layout

On larger screens:

A two-column layout:

Left: conversation editor (form + list of messages).

Right: phone-style preview of the conversation.

On smaller screens:

The same two areas can be stacked vertically.

The exact layout strategy is up to you, as long as:

Both the editor and preview remain usable.

The user understands clearly which area is for editing and which is for preview.

The layout should adapt reasonably to different viewport sizes.

5. Conversation editor (left side)

The editor should contain:

Participant settings

Inputs for the display names of Person A and Person B.

If left empty, fallback to default names.

Message creation form

A control to choose the sender (Person A or Person B).

A field to write the message text (multi-line input is preferable).

A button or action to add the message to the list.

Messages list

A visual list of all messages in order.

For each message, show at least:

Who sent it (using labels or names).

The text (truncated or full, as long as it remains readable).

For each message, provide controls to:

Edit.

Delete.

Reorder (e.g. move up/down or similar mechanism).

The exact UI elements (buttons, icons, etc.) are up to you, but actions should be clear.

6. Conversation preview (right side)
6.1. Smartphone mockup

The preview area should look like a smartphone screen:

A main rectangular area, with:

Rounded corners.

A border and/or shadow to evoke a device frame.

Inside the “screen”, there should be:

A top header zone.

A scrollable message area.

The exact visual style is flexible, but the end result should clearly evoke a messaging app.

6.2. Header area

The header at the top of the phone screen should contain:

A title corresponding to the chat:

Typically, the name of one of the participants (e.g. Person B, as if they were the contact).

Optional decorative elements (not mandatory, but allowed):

Fake status bar (time, battery, network).

Back arrow, call icons, etc.

These extra details can be static; they are mainly for realism.

6.3. Messages rendering

Messages should be rendered in sequence, using the current list from the editor.

For each message:

Alignment

Messages from one participant appear on the left.

Messages from the other participant appear on the right.

Which side is which is up to you, but it must be consistent.

Style

Each message appears as a chat bubble.

The two participants should have clearly different styles:

Different bubble colors.

Possibly different bubble shapes or subtle differences (optional).

Text must remain easy to read (contrast with background).

Size and wrapping

Bubbles should have a sensible maximum width so long messages wrap to multiple lines instead of stretching across the entire screen.

Line breaks entered by the user should be preserved.

Spacing

There should be visible spacing between messages.

When multiple consecutive messages come from the same sender, they may appear visually grouped (less spacing between them, if you choose to implement this).

Timestamps (optional)

Timestamps are not required.

If included, they can be generated automatically or left as a simple placeholder.

If present, they should be visually unobtrusive.

Background

The conversation area should have a background that makes the bubbles stand out (solid color or subtle pattern).

The preview does not need any user interaction besides scrolling; it is purely a visual representation of what was defined on the left.

7. State management and data handling

All data (messages, participant names, etc.) lives in the client.

There is no server communication.

The way you organize state (hooks, context, etc.) is up to you, as long as:

The editor and preview stay in sync.

Changes are reflected immediately.

Persistence (e.g. using local storage) is optional. If implemented, the goal would be to restore the last conversation when the user revisits the page.

8. UX and visual guidelines

The interface should be simple and understandable at first glance:

Clear distinction between “edit” area and “preview” area.

Clear labels on inputs and buttons.

The visual style of the chat should evoke a modern messaging app, without copying any brand exactly.

The design does not need to be pixel-perfect or heavily themed, but should:

Look clean.

Be reasonably polished.

Be easy to adjust later (e.g. via CSS variables or well-structured styles).

Errors (like trying to add an empty message) should be communicated in a minimal but visible way (text error message, hint, etc.).

9. Non-goals (for this version)

These are not required in the first version:

Exporting the preview as an image.

Handling more than two participants.

Sending real messages or connecting to any messaging service.

Support for images, emojis, or attachments in messages (plain text is enough to start).

10. Deliverables

A React-based frontend project that:

Implements the behavior described above.

Provides a usable UI for defining a conversation and previewing it.

Is viewable and usable on desktop and mobile screens (basic responsiveness).

Documentation (for example, a short README) explaining:

How to install and run the project locally.

Any assumptions or limitations you made (for example, how the smartphone layout is structured, how many messages the preview handles comfortably, etc.).

If anything in the description is ambiguous, you can make reasonable UI/UX decisions as long as you stay consistent with the main idea: a simple tool to create and visualize SMS-style conversations between two people, entirely in the browser with React, and no backend.
